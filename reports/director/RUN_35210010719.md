### Must-fix resolved: completion atomicity

The prior finding was that `handleComplete` executed the two coupled writes (todo status update + ContributionEntry creation) with `Promise.all`, which is not a transaction — failure A leaked an orphan ContributionEntry and a retry created a second one; failure B silently lost the ledger entry.

The repair now delivers a real atomic operation:

- **New use-case** `src/application/use-cases/completeTodoAtomic.ts` — validates via `planTodoCompletion`, then runs both writes inside `repos.withTransaction`.
- **Repository contract** `src/infrastructure/repositories/RepositoryFactory.ts` — `AllRepositories.withTransaction<T>` added. SQLite path delegates to `db.withTransactionAsync` (real rollback); in-memory path snapshots `InMemoryTodoRepository` + `InMemoryContributionEntryRepository` and restores on throw.
- **In-memory support** `src/infrastructure/repositories/InMemoryRepositories.ts` — `snapshot()/restoreFromSnapshot()` with deep copy of `beneficiaryMemberIds`.
- **UI** `app/(tabs)/todos.tsx` — `handleComplete` calls the single atomic use-case; `Promise.all` removed.
- **Failure-injection tests** in `__tests__/domain/todo-completion.test.ts` prove: (a) todo-update failure → 0 ContributionEntries and todo stays `todo`; (b) contribution-create failure → todo rolled back to `todo`; (c) retry after contribution failure → exactly 1 entry; (c2) retry after todo-update failure → exactly 1 entry. Ledger zero-sum holds.
- **Cost gate** `__tests__/domain/cost-gates-v3-05.test.ts` exercises `completeTodoAtomic` and asserts exactly 2 writes inside one transaction.

This satisfies backend frugal §7 ("Les changements couplés doivent employer batch/transaction/opération métier atomique").

## Next task: V3-06 — Groupes, invitations, identité, sync et backend frugal

V3-06 is a **frugal backend release criterion**, not polish. The roadmap and `docs/V3_BACKEND_FRUGAL.md` assign it concrete obligations that must be delivered and evidenced, not deferred to V3-08.

### Product scope

- Multi-groupes illimités, identité stable, tenant isolation.
- Options groupe Minutes|Points et compensation (already modeled in V3-01/V3-04) surfaced and persisted.
- Invitation réelle par lien/partage/deep-link quand disponible, acceptation simple, arrivée dans le groupe avec identité stable — reuse and extend the existing `InvitationGateway` / `LocalInvitationAdapter` abstraction rather than a parallel path.
- Aucune restriction de plan.

### Frugal backend obligations (must actually be delivered)

1. **Delta-only sync.** Every syncable object carries `id`, `groupId`, `createdAt`, `updatedAt`, `revision/version` and tombstone/deletion state. Each client keeps a per-group cursor; if local is at revision 1842 and the group at 1846, fetch only 1843..1846. Never download a whole collection to filter client-side.
2. **Lightweight change signal only if realtime is used.** Prefer a single `groups/{groupId}/syncState` revision signal, or foreground sync + explicit refresh + notifications. No permanent listeners over full history/tasks/expenses in parallel without measured justification.
3. **No N+1, no full scan.** Root/group screens must not fan out per-group member/balance/settings queries. Add instrumentation/tests detecting repeated repository calls.
4. **Atomic coupled operations.** Extend the V3-05 `withTransaction` pattern to any new coupled writes (invitation accept + membership, sync apply batches). Apply deltas transactionally then advance the cursor.
5. **Deterministic multi-device conflicts.** Cover simultaneous adds, same entry edited on two devices, offline deletion, return after weeks, invitation accepted during other changes. Accounting operations must never be lost by blind last-write-wins; when merge is unsafe, retain versions and resolve explicitly/deterministically.
6. **Hostile-backend rules.** No trust in client-supplied IDs/fields: verify authenticated identity, group membership, permissions, document type, mutable fields, tenant isolation, and impossibility of falsifying a balance without a corresponding business write. Test hostile scenarios.
7. **Firebase/Firestore only as adapter.** No Firestore types in domain; no accounting logic in React; local adapters must allow testing without cloud. No Cloud Function per gesture.
8. **Bounded and instrumented cost.** Instrument remote reads/session, writes/action, bytes synced, function calls. Define budgets per active user/group/1000 operations. A regression from 2 to 200 reads for the same action is a release finding.

### Required evidence

`tests`, `audit`, `cost-evidence` — including: sync after a few remote changes fetches only deltas; no N+1 or unjustified mass listener; no blind last-write-wins on accounting operations; backend rules block cross-tenant reads and balance falsification; remote reads/writes instrumentable and bounded.
