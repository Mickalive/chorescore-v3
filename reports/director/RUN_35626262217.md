## Summary

The audit accepted the V3-08 repair cycle. The candidate fixes the trusted finalizer E2E stuck-detector cascade from Actions run 35617229931, where the release job failed at the "Android API 35 install, launch and golden path" step after ~18m58s while all product/privacy/cost gates and the APK build passed. The root cause: the stuck-app detector (4 consecutive empty dumps = 2-4 min) fired during the SQLite demo sign-in phase (1-3 min on slow emulators) because only the `waitFor('Demarrer')` call had a per-wait grace; the next `waitFor` (e.g. Appartement) force-stopped a healthy app, and the relaunch + cold-start cascade exhausted the step budget.

The fix introduces a **global cold-start grace** anchored to app launch time (`_appLaunchTime` set in `launch()`) that protects ALL `waitFor` calls during the launch phase for 450s, raises `STUCK_APP_THRESHOLD` from 4 to 8, and resets the grace on every force-stop/relaunch path. The delta is confined to one file — zero product code changed, so V3-01 through V3-07 invariants are preserved.

V3-08 is the **final criterion** on the V3 roadmap. V3-01 through V3-07 are already complete. The Builder has no further work.

## Why this fixes the blocker

| Mechanism | Before | After |
|---|---|---|
| Cold-start grace scope | Per-wait only (`graceMs` on Demarrer) | **Global**: `_appLaunchTime` set in `launch()`; ALL `waitFor` calls protected for 450 s since launch — covers cold start, demo sign-in and initial rendering |
| `STUCK_APP_THRESHOLD` | 4 (~2-4 min) | **8** (~4-8 min) before recovery after grace expiry |
| Grace reset on relaunch | — | `_appLaunchTime = Date.now()` on every force-stop/relaunch path (crash detector, pidof exit 1, APP STUCK) |

The per-wait `graceMs` remains as an additional overlay (`inPerWaitGrace || inGlobalGrace`). The `waitFor` timeouts remain the ultimate bound (900 s Demarrer, 300 s mid-path), so a genuinely stuck app still fails with diagnostics. The existing `FORCE_STOP_RECOVERY_MS` per-relaunch recovery is preserved unchanged.
