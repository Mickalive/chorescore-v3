## What was attempted

The candidate introduces a stuck-app detector in `waitFor()`: after `STUCK_APP_THRESHOLD=4` consecutive successful-but-empty UI dumps (app alive, no expected label found), the script force-stops and relaunches the app. This targets the failure mode from trusted finalizer run 35530222887 where the app process survived but React Native was hung, and the pidof-based crash detector did nothing while the script burned through the full timeout doing 30-60s dumps that always miss.

## Must-fix findings

### 1. Stuck-app detector false-positives on dump-cache hits (critical)

**Path:** `scripts/e2e-android.js`

**Problem:** `consecutiveEmptyMatchCount` increments whenever `dumpFailures <= previousDumpFailures`, which is also true when `findNodes()` returns from the 30s dump cache without running any dump. After any single non-matching dump, the 500ms loop sleep reaches the threshold of 4 in ~1.5-2s of cache hits and force-stops + relaunches a healthy app that is merely mid-cold-start or mid-screen-transition. Loop simulation confirmed **3 false-positive force-stops during a normal 120s cold start** (t=1.5s, 60s, 118.5s). This breaks the golden path E2E the trusted finalizer runs (step 7): `waitFor('Demarrer', 600000)` with splash-screen warm-up cache force-stops the app ~2s after the wait starts and repeats, so the app never finishes cold start.

**Required fix:** Increment `consecutiveEmptyMatchCount` only when a real dump ran (cache miss) and returned no matching node. Concretely: expose a `fromCache` flag from `dumpUi()` (or compare `_dumpCacheTime` before/after the `findNodes` call) and guard the increment on the dump actually having executed; cache hits must neither increment nor reset the counter. Keep the force-stop + relaunch recovery and the counter resets on crash/dump-failure/stuck recovery.

**Verification:** Re-run the loop simulation: a 120s cold start must complete with 0 force-stops; a genuinely stuck app (alive process, valid dumps, no target node for >4 real dumps) must still trigger exactly one force-stop + relaunch. Full trusted verification must stay exit 0.

### 2. Weak contract test (must-fix)

**Path:** `__tests__/domain/v3-08-finalizer-wrapper.test.ts`

**Problem:** The new test only asserts static strings (`APP STUCK`, `consecutiveEmptyMatchCount`, `STUCK_APP_THRESHOLD`, force-stop, monkey, counter reset). It passes 19/19 with the buggy implementation and therefore gives false confidence that the repair is correct; it does not guard the actual detector logic (increment only on real dumps, not cache hits).

**Required fix:** Strengthen the contract test to assert the cache-miss guard: e.g. assert `dumpUi()` returns a `fromCache` flag (or equivalent) and that the `consecutiveEmptyMatchCount` increment is conditioned on a real dump having run (cache miss). Reverting the guard must fail the test.

**Verification:** Test suite must fail when the increment guard is removed and pass when the guard is present; full trusted verification stays exit 0.
