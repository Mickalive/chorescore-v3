However, four new must-fix findings prevent acceptance:

### MF-1 — Equal-timestamp pagination gap (skipped entries)

The cursor is exclusive on `occurredAt` alone with no secondary sort key. When >PAGE_SIZE entries share one timestamp, the first page returns PAGE_SIZE of them, the cursor becomes that timestamp, and the next page excludes ALL entries with that timestamp — the overflow entries are permanently unreachable. The new merged-pagination tests only use distinct timestamps (1 hour apart), so the equal-timestamp boundary case is untested.

**Required fix:** Composite cursor (occurredAt + id) with deterministic secondary sort key in both InMemory and SQLite repositories. Add a test seeding ≥PAGE_SIZE+5 entries with one identical occurredAt plus older entries, asserting every seeded id is reachable exactly once.

### MF-2 — 'Charger plus' race produces duplicate ids

No in-flight guard on `loadHistory(true)`: two rapid taps on 'Charger plus' issue two concurrent fetches with the same cursor state, both append the same page to the accumulated arrays, and `paginateActivityLog` does not dedupe — producing duplicate rows with duplicate ids.

**Required fix:** In-flight guard (ref) that skips or queues a second call, OR dedupe by entry id in the merge step. Add a test firing two concurrent load-more calls and asserting no duplicate ids.

### MF-3 — Share message uses current household unit instead of entry unit

The share message formats the contribution value with the CURRENT household unit (`householdUnit === 'minutes' ? 'min' : 'pts'`) instead of the entry's stored `unit` field. After a group switches Minutes↔Points, old minutes entries would be shared as "15 pts" — a silent unit reinterpretation of history, violating constitution §18. The history row display has the same issue.

**Required fix:** Use `e.unit` in the share message and in the history row display instead of the current household unit.

### MF-4 — Custom-split validation does not block submit

The inline custom-split sum validation displays an error but does not block submit: the Button disabled condition is only `!title || !amountRaw || isSubmitting`, and repositories persist expenses without write-time validation. An invalid custom-split expense can enter the ledger and later break financial balance computation.

**Required fix:** Block submit when `sum(customShares) != amountMinor` (disable button or early-return in submitExpense with the inline error).
