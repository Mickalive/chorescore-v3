## What happened

The candidate generalized ANR overlay handling in `scripts/e2e-android.js`. The previous handler only dismissed SystemUI ANRs (`"System UI isn't responding"`), leaving app-specific ANRs (`"ChoreScore isn't responding"`) as real failures. On degraded API 35 x86_64 emulators, the app-specific ANR dialog covers the screen during Hermes init / SQLite schema creation / demo fixture seeding, and the main thread is too blocked to recover within the Wait grace — creating a Wait→ANR→Wait loop that burns the entire 900s Demarrer timeout.

The repair:
- Detects ANY `android:id/alertTitle` whose text includes `"isn't responding"`
- Distinguishes SystemUI vs app ANR by absence of `'System UI'` in the title
- SystemUI ANR → tap Wait only (unchanged, safe)
- App ANR → tap Wait + `am force-stop` + `monkey` LAUNCHER relaunch + 15s init sleep
- Resets `globalThis._lastForceStopTime` and `globalThis._appLaunchTime` to prevent kill-loop

Kill-loop guards are verified: the stuck detector only counts empty dumps when `sinceLastForceStop >= FORCE_STOP_RECOVERY_MS` (300s) AND `globalGraceElapsed` (COLD_START_GRACE_MS = 450s). A force-stop suspends stuck detection for 5 minutes.
