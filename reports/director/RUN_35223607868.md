## Must-fix findings

### 1. Sync pipeline not wired into the production SQLite path
`createSqliteRepositories()` returns plain `SqliteSyncStateRepository` and plain Sqlite business repos with no `MaterializingSyncState` and no sync-recording wrappers. `applyDeltas` still only buffers pulled records into `sync_records` (cursor advances) without materializing into business tables, and local business writes never call `storeLocalRecords`, so `pushDeltas` has no payloads. This is the previous audit's must-fix #1, still unfixed for the production path. Even in the in-memory path, only contributions/expenses/todos/settlements are wrapped — persistent_tasks, members, memberships and households writes never record dirty records.

**Required fix:** Wire materialization + dirty-record recording into the SQLite path for all 8 `SYNC_COLLECTIONS`; add a contract test run against the SQLite implementation.

### 2. applyDeltas not transactional; cursor advances before materialization
`inner.applyDeltas` (which advances the cursor) runs first, then `materializeDeltas` runs outside any transaction. A failure during materialization leaves the cursor advanced with records only in the buffer — the next pull will not re-fetch them, silently losing business data.

**Required fix:** Materialize first, then advance the cursor, atomically (extend in-memory snapshot coverage; use `withTransactionAsync` on SQLite); roll back both on failure.

### 3. Tenant isolation and balance integrity unenforced in data-access path
`requireHouseholdMembership`, `requireRole`, `assertLedgerWrite` have zero callers outside `authorizationRules.ts`. Repositories accept any `householdId` without caller-membership context. Hostile tests exercise the pure functions, not the repository path. Previous audit's must-fix #4, still unfixed.

**Required fix:** Enforce membership scoping in the data-access path (scoped repository facade or use-case checks); route ledger mutations through append/revision/tombstone with `assertLedgerWrite`-style validation; hostile tests through the actual repository path.

### 4. Conflict resolution incomplete / blind in places
- `case 'households'` does blind `repos.households.update` with no `resolveConflict`.
- Local revision is fabricated as `0` in `resolveConflict` calls — remote (revision ≥ 1) always wins, a local offline edit of the same id is silently discarded.
- SQLite `applyDeltas` remains blind `INSERT OR REPLACE`.

**Required fix:** Persist and pass the real local revision; apply `resolveConflict` to households (and members/memberships); make SQLite `applyDeltas` use deterministic resolution; add a materializer-level test where local revision > remote revision and assert the local version wins.
