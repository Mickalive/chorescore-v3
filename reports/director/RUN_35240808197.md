## Must-fix findings (current cycle)

### 1. Cursor advance and materialization not in a single transaction
`syncEngine.ts` lines 90-102 calls `syncState.applyDeltas(...)` then `syncState.setCursor(...)` as sequential top-level statements. `RepositoryFactory.ts` `withTransaction` wraps only `materializeDeltas + storeLocalRecords` (lines 195-205); the cursor write commits separately. Additionally, the in-memory `withTransaction` still snapshots only `contributionRepo` and `todoRepo` (lines 278-279) — it was NOT extended to all affected repos (expenses, settlements, tasks, members, memberships, households, sync buffer). A mid-transaction failure leaves partial writes.

**Required fix:** Move the cursor advance inside the same transaction as materialization. Extend in-memory `withTransaction` to snapshot/restore ALL affected repos. Use `withTransactionAsync` on SQLite. Add a test that injects a real failing materialization and asserts the cursor did not advance AND no business table was partially updated.

### 2. Local dirty record overwritten when local wins conflict
When a local record has a higher revision than the remote, `MaterializingSyncState.applyDeltas` calls `storeLocalRecords` with the REMOTE records after materialization (RepositoryFactory.ts line 202). Both `InMemoryRepositories` (lines 611-618: `existing[idx] = { ...record }`) and `SqliteRepositories` (lines 1204-1208: `INSERT OR REPLACE INTO sync_records`) replace the buffer row by id. The local dirty record (higher revision, local winner) is overwritten by the remote record, so `pushDeltas` sends the remote payload or nothing — the local offline edit is never propagated.

**Required fix:** When the local record wins the conflict, preserve the local dirty record in the buffer (do not overwrite it with the remote record). Only store the remote record when the remote wins. Add a test: local write → pull of same id with lower remote revision → assert business entity is LOCAL AND `getDirtyRecords` still returns the LOCAL payload.

### 3. Membership scoping not enforced in the app's data-access path
`ScopedRepositoryFacade` exists and hostile tests prove it rejects non-member reads/writes, but it is imported only by the test file. `AppContext.tsx` and screens use the unscoped repos directly (repos.households.create, repos.memberships.create, repos.members.create, repos.contributions.*, etc.), so no membership verification happens for product reads/writes.

**Required fix:** Wire the scoped facade (or equivalent membership check) into the data-access path actually used by the app. AppContext/use-cases must obtain repos scoped to the current user so every read/write verifies membership. Hostile tests must exercise the path the app uses, not only a manually constructed facade.

### 4. No test exercises the sync pipeline on the SQLite repository path
All new sync tests use `createInMemoryRepositories()` exclusively. The existing `repositories.test.ts` exercises raw Sqlite*Repository CRUD but never the `MaterializingSyncState + SyncRecording` wrapper wiring on the SQLite path — no remote delta materializing into a SQLite business table, no local write appearing in SQLite `getDirtyRecords`.

**Required fix:** Add a test that runs the sync pipeline (applyDeltas materialization + wrapper dirty recording + pushDeltas) against the SQLite-backed repositories (using the mocked expo-sqlite driver), or a shared contract test executed against both implementations, proving remote delta → business record readable and local write → getDirtyRecords payload.
