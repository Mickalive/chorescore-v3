### Must-fix: Completion atomicity

**The problem.** `app/(tabs)/todos.tsx` `handleComplete` executes two coupled writes — todo status update + ContributionEntry creation — via `Promise.all`, which is not a transaction:

- **Failure A:** If `repos.todos.update` rejects after `repos.contributions.create` resolves → orphan ContributionEntry exists while the todo stays active. User sees error, retries → **second** ContributionEntry created. Violates "exactement une ContributionEntry atomique."
- **Failure B:** If `repos.contributions.create` rejects after todo update resolved → todo marked completed and filtered out with no ledger entry. Silent loss.

The independent auditor's probe confirmed this: deleting the todo before `Promise.all` made `todoRepo.update` throw while `contribRepo.create` succeeded — `contributionsCreated=1` leaked.

**Required fix:** Add a repository-level transaction (SQLite `withTransactionAsync` wrapping the todo update + contribution insert, with in-memory equivalent) or a completion use-case in the domain/application layer that writes both in one transaction. The UI must call that single atomic operation. Add failure-atomicity tests:
- (a) Todo update fails → no ContributionEntry created
- (b) Contribution create fails → todo not marked completed
- (c) Retry after any failure cannot produce a second ContributionEntry

**Verification:** Failure-injection tests against the transactional completion path: force todo update to reject → assert `contribRepo.getByHousehold` returns 0 entries; force contribution create to reject → assert todo status remains `'todo'`; then complete successfully → assert exactly 1 ContributionEntry exists.
