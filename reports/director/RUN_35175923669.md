## Remaining must-fix findings

### 1. Settlement delta double-applied (critical)
`handleCompenserConfirm` applies the settlement delta directly to `snapshotRef.current` (both contribution and money), then calls `emitDataChange('settlement', ...)`. The screen's own `handleDataChange` receives this event synchronously; its closure captures the render-time `settlements` state which does NOT include the just-created settlement. It re-reads `repos.settlements.getByHousehold`, computes `added` against the stale old-ids, and applies the delta a second time. Simulation: contribution a=0/b=0 (expected a=15/b=-15), money a=-500/b=500 (expected a=-1000/b=1000).

**Fix:** Either (a) do not emit 'settlement' from `handleCompenserConfirm` since the screen already applied the delta and updated state, or (b) make `handleDataChange` idempotent by tracking processed settlement ids in a ref that is updated synchronously when the delta is applied, or (c) pass the created entity in the signal payload and skip the re-read for self-created settlements. Add a test asserting snapshot == full replay after repos.settlements.create.

### 2. Custom-split expense delta broken
`handleDataChange` always applies equal-split math (`share = floor(amountMinor/count)`, remainder to first participant) regardless of `splitMode`. A custom-split expense (e.g. 1000 CHF with shares a=700/b=300) adds a delta of a=+500/b=-500 instead of the correct a=+300/b=-300. The all-time money snapshot is corrupted for every custom-split expense added via the Add tab.

**Fix:** Reuse `allocateExpense(entry)` or replicate its `splitMode`-aware logic so the delta matches full replay for both equal and custom splits. Add a test asserting delta == full replay for a custom-split expense.

### 3. Edits and deletes emit no signal (regression)
`submitEdit` and `handleDelete` in `add.tsx` emit no data-change signal. The pristine baseline reloaded all data on every focus. The candidate removed that safety net without covering edit/delete. After editing or deleting an entry in the Add tab, the Balances screen keeps stale state indefinitely.

**Fix:** Emit the appropriate data-change signal after successful edit and delete (e.g. `emitDataChange('contribution'|'expense', currentHouseholdId)`). Make the Balances delta handler process removals (detect removed ids, apply remove deltas) and modifications (remove old effect, apply new). Add a test asserting snapshot == full replay after a delete and after an edit.

### 4. Required screen-level test still absent
The test "Balances screen subscribes to data-change signal" simulates the pub/sub contract with a local Set — it never renders the screen, never imports AppContext, and never asserts the actual screen subscribes. The header claim that the screen subscribes to a data-change signal remains unproven.

**Fix:** Add a test that either (a) renders the Balances screen against fake repositories, adds/edits/deletes an entry, emits the data-change signal, and asserts the view updates via delta with bounded repository call counts (no full re-read on focus), or (b) imports the real AppContext/Balances wiring and asserts the screen subscribes to `subscribeToDataChanges` and applies deltas. Remove or substantiate the header claim.
