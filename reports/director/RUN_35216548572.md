## Must-fix findings

### 1. Sync pipeline not functional end-to-end
`applyDeltas` in both `InMemoryRepositories.ts` and `SqliteRepositories.ts` only writes into the `sync_records` buffer table via `INSERT OR REPLACE`. It never materializes pulled payloads into business tables (`contribution_entries`, `expense_entries`, `settlements`, `todo_items`, `persistent_tasks`, `members`, `memberships`, `households`), so remote changes never reach business data. Conversely, `storeLocalRecords` has **zero callers** anywhere in `src/` — local writes never populate the buffer, so `getDirtyRecords` is always empty and `pushDeltas` sends nothing. The sync cursor advances but no data moves.

**Required fix:** Wire the pipeline. `applyDeltas` must materialize each pulled record into its business table (or replay payloads through the ledger/use-cases) inside a transaction, then advance the cursor. Every local business write must record its dirty record via `storeLocalRecords` (or equivalent) so `pushDeltas` has real payloads.

### 2. No invitation UI
`invitationService.createInvitation` and `planInvitationAcceptance` exist as domain services and are tested, but there is **no create-invitation screen, no share-sheet action, no accept screen, and no deep-link route** (`app.json` declares scheme `chorescore` but no `/join/:token` route). The createInvitation port (`src/application/ports/index.ts:130-131`) is unused outside tests. Constitution §4 requires "un parcours d'invitation réellement utilisable."

**Required fix:** Add a real invitation flow: an invite action in the group (share sheet with the link), a deep-link route (e.g. `/join/:token`) that resolves and accepts the invitation atomically, and an honest adapter behind the existing invitation port. Free of any plan/entitlement gating.

### 3. No group-options UI
`balances.tsx` gates compensation on `crossLedgerCompensationEnabled` (~line 519) and tells the user to activate it "dans les options du groupe" (~line 835), but **no such options screen exists**. `unitChangeService.planUnitChange` is only called in tests. Constitution §8 requires the compensation flow to be exercisable by users.

**Required fix:** Add a group-options screen reachable from the group (per constitution §3, "Options restent hors de la navigation principale") exposing: contribution unit Minutes|Points with confirmation that historical entries keep their provenance/unit (no silent conversion), and the compensation toggle + group-defined rate.

### 4. Authorization rules unenforced, blind LWW in applyDeltas
`requireHouseholdMembership`, `requireRole`, `assertLedgerWrite`, `resolveConflict`, and `resolveConflicts` are only exercised by tests. No repository or use-case checks tenant membership before reads/writes. `applyDeltas` performs blind last-write-wins by `(id, collection)` without revision comparison, violating constitution §9 and backend-frugal §9 ("les opérations comptables ne doivent jamais être perdues par un simple last-write-wins aveugle").

**Required fix:** Enforce tenant isolation and balance integrity in the data-access path (repository or use-case level). `applyDeltas` must use deterministic revision/timestamp/id conflict resolution instead of blind overwrite. Add hostile tests (cross-tenant read blocked, balance falsification rejected, concurrent same-id edits resolved deterministically).

### 5. Tests only assert buffer/cursor mechanics
The 731-line V3-06 test suite covers invitation lifecycle, unit change, and delta-only cursor ranges, but **never proves that a pulled delta materializes into business data** or that a local write is queued for push. This is why the non-functional pipeline above passes the suite.

**Required fix:** Add end-to-end sync tests: apply a remote delta and assert the business record is readable and balances are updated; create a local write and assert it appears in `getDirtyRecords` and is pushed; simulate a conflict and assert the deterministic resolver outcome. These tests must fail until the pipeline is wired.
