## Must-fix finding — completion is not atomic

**Path:** `app/(tabs)/todos.tsx` (`handleComplete`, lines 247-254) and `__tests__/domain/todo-completion.test.ts` (lines 203-245).

**Problem.** The two coupled writes — todo status update and ContributionEntry creation — are executed with `Promise.all`, which is not atomic:

- **Failure A** (todo update rejects after contribution create resolved): an orphan ContributionEntry exists while the todo stays active. The user sees `Impossible de terminer la tache` and a retry creates a **second** ContributionEntry — violating the acceptance `exactement une ContributionEntry atomique`.
- **Failure B** (contribution create rejects after todo update resolved): the todo is marked completed and filtered out of the list with no ledger entry — silent loss of the contribution.

The test `creating the contribution and updating the todo is atomic in the repos` only exercises the success path and asserts "both succeed or both fail" without ever injecting a failure — a weak test that does not guard the invariant. Backend frugal §7: *« Les changements couplés doivent employer batch/transaction/opération métier atomique. »*

**Evidence (independent probe).** I wrote a temporary test that deletes the todo before the `Promise.all` (so `todoRepo.update` rejects) while `contribRepo.create` runs: console output `todoUpdateFailed= true contributionsCreated= 1` — the contribution leaked despite the "atomic" failure. The repository layer (`InMemoryRepositories.ts`, `SqliteRepositories.ts`) exposes no transaction/batch API, so the UI-level `Promise.all` is the only "atomicity" mechanism. Probe removed afterward; working tree restored.

**Required fix.** Execute the completion as a single atomic operation: a repository-level transaction (e.g. SQLite `withTransactionAsync` wrapping the todo update + contribution insert, with an in-memory equivalent) or a completion use-case in the domain/application layer that writes both in one transaction, called by the UI. Add failure-atomicity tests: (a) todo update fails → no ContributionEntry created; (b) contribution create fails → todo not marked completed; (c) retry after any failure cannot produce a second ContributionEntry. Update the existing success-path test to use the atomic operation instead of `Promise.all`.

**Verification.** Failure-injection tests against the transactional completion path: force the todo update to reject and assert `contribRepo.getByHousehold` returns 0 entries; force the contribution create to reject and assert the todo status remains `'todo'`; then complete successfully and assert exactly 1 ContributionEntry exists.

2. **Reminder-cancel block is empty** — honest today (`isAvailable()` false), but when a real notification port is wired, completed todos would leave orphan scheduled reminders; persist the notification id on `TodoItem` in a later cycle.
3. **Value field not prefilled from PersistentTask** — `startComplete` leaves `value: ''`; the constitution allows the default to come from the PersistentTask (`peut provenir`). UX convenience gap, not an acceptance failure.
4. **`parseFloat` accepts fractional values / trailing garbage** — the domain allows finite positive values, so this is consistent; minor.

## Decision

The candidate is otherwise coherent, well-tested on the success path, honest about ports, free of chrono/premium, local-first and cost-bounded; it is preserved as the WIP baseline so the next cycle repairs the atomicity gap instead of rebuilding.
