## Must-fix findings

### MF-1 — In-memory `withTransaction` snapshot coverage incomplete
- **Path:** `src/infrastructure/repositories/RepositoryFactory.ts` (lines 356–374)
- **Problem:** Only `contributionRepo`, `todoRepo` and sync buffer/cursor state are snapshotted. Expenses, settlements, tasks, members, memberships and households are not, so a mid-transaction failure leaves partial writes in those tables. Only `InMemoryContributionEntryRepository` and `InMemoryTodoRepository` implement snapshot/restore.
- **Evidence:** Independent verification — a transaction writing an expense + contribution then throwing leaves the expense in the business table (`expenses after rollback: 1 (expected 0)`) while the contribution is rolled back (`contributions after rollback: 0`).
- **Required fix:** Add `snapshot()/restoreFromSnapshot()` to all remaining in-memory business repos and include them in `withTransaction`; add a failure-injection test asserting ALL business tables unchanged after rollback.

### MF-2 — Failure-injection test doesn't exercise the production path
- **Path:** `__tests__/domain/v3-06-repair-sync-authorization.test.ts` (Finding #1 block, lines 33–191)
- **Problem:** The test builds a hand-rolled replica of `MaterializingSyncState` (anonymous class with its own `applyDeltas`) instead of calling the production `repos.syncState.applyDeltas`, and only asserts the contribution table + cursor ≤ 1. It would pass even if production `applyDeltas` advanced the cursor outside the transaction or left partial writes elsewhere.
- **Required fix:** Inject a throwing repo into the real repository set, call the production `applyDeltas`/`pullDeltas`, and assert the cursor did not advance AND every business table is unchanged.

### MF-3 — Hostile tests don't exercise the app path
- **Path:** `__tests__/domain/v3-06-repair-sync-authorization.test.ts` (Finding #3 block, lines 348–466)
- **Problem:** All hostile tests call `createScopedRepositories` manually. No `AppProvider`/`useApp` test exists anywhere in the suite, so nothing proves the AppContext wiring actually rejects cross-tenant access.
- **Required fix:** Add hostile tests driving the app-level path (render `AppProvider`, sign in, assert CROSS_TENANT rejection through `useApp()` repos, and legitimate member access succeeds).

### MF-4 — AppContext scoping breaks invitation acceptance and stale-scopes across sign-in/sign-out
- **Path:** `src/features/app/AppContext.tsx` (signIn/signOut) + `app/join/[token].tsx`
- **Problem:** (a) The join flow reads `households.getById` and `memberships.getByHousehold` BEFORE the user is a member → `AuthorizationError CROSS_TENANT`; a signed-in user can never accept an invitation. (b) `signOut` doesn't reset `reposRef`, so a second sign-in double-wraps; the stale inner caller blocks legitimate access.
- **Evidence:** Independent verification — `JOIN FLOW BREAKS: CROSS_TENANT` on household read; `MEMBERSHIP CREATE BLOCKED: CROSS_TENANT`; `B reads own group h-B BLOCKED (BUG): CROSS_TENANT` after A signed out and B signed in.
- **Required fix:** Invitation-token-authorized read + membership creation for the invitee (or a dedicated join use-case); re-scope from raw repos on every sign-in.

### MF-5 — SQLite sync tests don't run the actual pipeline
- **Path:** `__tests__/infrastructure/repositories.test.ts` (Finding #4 block, lines 546–700)
- **Problem:** Tests use raw `SqliteSyncStateRepository` + `SqliteContributionEntryRepository`, manually seed the business table and manually construct dirty records. `MaterializingSyncState` materialization and `SyncRecording` wrapper recording are never exercised on the SQLite path.
- **Required fix:** Wire the SQLite repos exactly as the factory does (raw repos + wrappers + materializer) and prove remote delta → business record readable, local write → `getDirtyRecords` payload, `pushDeltas` sends it.

### MF-6 — Persistent tasks and invitations remain unscoped in the app path
- **Path:** `src/infrastructure/repositories/ScopedRepositoryFacade.ts` (lines 67–86)
- **Problem:** `repos.tasks` (`getByHousehold`/`create`/`delete`) and `repos.invitations` (`getByHousehold`/`create`) are household-scoped repos used by the screens (add.tsx, todos.tsx, invite.tsx, join/[token].tsx) but are left unscoped — no membership check.
- **Required fix:** Add `ScopedPersistentTaskRepository` and scope invitation reads (token-based reads remain invitation-authorized); add a hostile test proving a non-member is blocked from another household's persistent tasks.

## Conclusion

The candidate is a coherent, testable improvement and must be preserved as the WIP baseline. Trusted verification passed and no V3-01..V3-05 regression was found. However, six must-fix findings remain — most critically the partial-write rollback gap (MF-1), the join-flow regression introduced by the scoping wiring (MF-4), and the fact that the new tests do not exercise the production paths they claim to cover (MF-2, MF-3, MF-5). Decision: **repair**.
