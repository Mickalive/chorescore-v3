## 7. Findings

### 7.1 Non-must-fix — cold-start snapshot skipped if the app is dead at 30s

- **Path:** `scripts/e2e-android.js` (cold-start snapshot in `launch()`)
- **Problem:** The 30s snapshot is skipped entirely if the first `pidof` throws (app dead at 30s — `pidof` exits 1 and `execFileSync` throws), so a crash during the earliest Hermes window produces no `COLD-START [30s]` line. Minor diagnostic gap only: the `waitFor` app-alive check (every 30s) and the timeout diagnostics still capture crash evidence.
- **Evidence:** `launch()` wraps the whole snapshot in `try/catch (_) {}`; the existing app-alive check in `waitFor` handles `err.status === 1` explicitly and relaunches.
- **mustFix:** false
- **Required fix:** None for acceptance. Optional hardening: split the pidof check from the dumpsys/logcat capture so a dead process still logs `pid=NOT FOUND` and captures logcat.
- **Verification:** The Demarrer wait diagnostics (every 120s) will show `pid=NOT FOUND` if the app dies mid-wait.

### 7.2 Non-must-fix — mid-wait logcat uses default retries (could reconnect)

- **Path:** `scripts/e2e-android.js` (mid-wait logcat diagnostic)
- **Problem:** `adb(['logcat', '-d', '-t', '60'], { timeoutMs: 10_000 })` uses default `retries=3` with `allowReconnect=true`, so a logcat timeout could trigger `adbReconnect` (~10s) inside a wait loop. Consistent with existing patterns (app-alive pidof check, timeout logcat capture) and bounded (10s timeout, 120s cadence), so it does not materially threaten the 900s Demarrer window.
- **Evidence:** `adb()` defaults; same pattern at L532 and L663; `adbReconnect` is the script's established recovery mechanism.
- **mustFix:** false
- **Required fix:** None for acceptance. Optional refinement: `{ retries: 1, allowReconnect: false }` on diagnostic calls.
- **Verification:** Diagnostics are read-only and bounded; the wait deadline is wall-clock based.
