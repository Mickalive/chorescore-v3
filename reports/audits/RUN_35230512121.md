## Must-fix findings

### 1. Cursor advance is outside the transaction; in-memory snapshot coverage not extended

`pullDeltas` calls `applyDeltas(...)` and then `setCursor(...)` as two separate top-level
statements (`syncEngine.ts` L90–102). `MaterializingSyncState.applyDeltas` wraps only
`materializeDeltas` + `storeLocalRecords` in `withTransaction` (`RepositoryFactory.ts` L195–205);
the cursor write commits separately. The in-memory `withTransaction` still snapshots only
`contributionRepo` and `todoRepo` (L278–279) — expenses, settlements, tasks, members, memberships,
households and the sync buffer are not covered, so a mid-transaction failure leaves partial writes.
The criterion explicitly requires cursor advance + materialization in a single transaction with
snapshot coverage extended to all affected repos.

The test `materialization failure rolls back cursor advance` does not inject a real failure:
malformed JSON is silently skipped (`parsePayload` → null → `continue`), nothing throws, nothing
rolls back, and the test never asserts the cursor did not advance.

### 2. Local dirty record is overwritten by the remote record when local wins

When a local dirty record wins a conflict (higher revision), `applyDeltas` still calls
`storeLocalRecords` with the **remote** records, and both implementations replace the buffer row by
id (`existing[idx] = {...record}` / `INSERT OR REPLACE`). The local edit is then never pushed —
silently lost from the sync pipeline. This defeats the criterion's intent that local offline edits
are not discarded.

### 3. Scoped facade is not wired into the app's data-access path

`ScopedRepositoryFacade` is imported only by the test file. `AppContext.tsx` and the screens use
the unscoped repos directly, so no membership verification happens for actual product reads/writes.
The hostile tests prove the facade works when manually constructed, but the criterion requires
enforcement in the data-access path the app actually uses.

### 4. No test exercises the SQLite repository path for the sync pipeline

The criterion requires a test proving `remote delta → business record readable` and
`local write → getDirtyRecords payload` on the SQLite path (or a shared contract test on both
implementations). The new tests only use `createInMemoryRepositories()`; `repositories.test.ts`
exercises raw `Sqlite*Repository` CRUD but never the `MaterializingSyncState` + wrapper wiring.

## Should-fix findings (non-blocking)

- **Members conflict resolution incomplete**: existing members are never updated (no-op), member
  tombstones are a no-op, and `SyncRecordingMemberRepository` has no update/delete — remote member
  changes cannot be synced beyond creation.
- **`extractLocalRevisions` full buffer scan**: `getDirtyRecords(householdId, collection, 0)` reads
  the entire (never-pruned) sync buffer per collection per pull — O(total history) local reads for a
  common action, against V3_BACKEND_FRUGAL §4.
- **Membership delete records no tombstone**: `SyncRecordingMembershipRepository.delete` hard-deletes
  without a dirty record, so membership removal never propagates to other devices.

## Conclusion

The candidate is a coherent, mostly-correct repair baseline with real progress on all four findings,
but four must-fix gaps remain (transactional atomicity + snapshot coverage + failure-injection test,
local-wins push-queue preservation, facade wiring into the app path, SQLite-path sync test).
Trusted verification passed, but the acceptance criteria are not fully met.

**Decision: `repair`** — preserve this delta as the WIP baseline and repair the must-fix findings in
the next cycle.
