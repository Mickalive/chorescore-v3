## Must-fix findings

### 1. Settlement created in the Balances screen is double-applied to the materialized snapshot
`handleCompenserConfirm` applies the settlement delta directly to `snapshotRef.current` (contribution + money), then calls `emitDataChange('settlement', currentHouseholdId)`. The screen's own subscribed `handleDataChange` receives the event synchronously; its closure captures the render-time `settlements` state, which does **not** include the just-created settlement (React state updates never mutate the current render's closure). The handler re-reads the repo (which now contains the settlement), computes `added` against the stale `oldIds`, and applies the delta a **second** time. Independently verified by simulation with React closure semantics: after a 15-min/CHF 5.00 settlement on contribution a=+30/b=−30 and money a=−1500/b=+1500, the snapshot ends at contribution a=0/b=0 (expected a=15/b=−15) and money a=−500/b=500 (expected a=−1000/b=1000). Both all-time views are corrupted after every compensation; the ledger stays zero-sum so the « Somme nulle » badge masks the error. **mustFix.**

### 2. Expense delta always applies equal-split math, corrupting custom-split expenses
The `expense` case in `handleDataChange` computes `share = floor(amountMinor / count)` and distributes the remainder to the first participants, regardless of `entry.splitMode`. The Add tab supports custom splits and emits `expense` for them. Verified by simulation: a custom-split expense of 1000 CHF (a=700, b=300) yields delta a=+500/b=−500, while `allocateExpense`/`calculateFinancialBalances` yield a=+300/b=−300. The all-time money view (which reads the snapshot) is wrong; period views recompute from state arrays and stay correct. **mustFix.**

### 3. Edits and deletes in the Add tab emit no signal → Balances stale indefinitely
`submitEdit` and `handleDelete` in add.tsx never call `emitDataChange`, and the Balances focus effect no longer full-reloads (only on household change). The pristine baseline reloaded all data on every focus; the candidate removed that safety net without covering edit/delete. After editing or deleting an entry in the Add tab, the Balances screen keeps stale state and a stale all-time snapshot until a household change or remount. The task explicitly requires deltas for entries « added/removed in other tabs ». **mustFix.**

### 4. Required screen-level test not delivered; header claim still unproven
The task requires either rendering the Balances screen against a fake repo and asserting delta update via repository call counts, or asserting the screen subscribes to a data-change signal. The test « Balances screen subscribes to data-change signal » simulates the pub/sub contract with a local `Set` — it never renders the screen, never imports AppContext, and never asserts the actual screen subscribes. Header claim #5 (« The Balances screen subscribes to a data-change signal from AppContext and applies incremental deltas instead of full re-reads on focus ») therefore remains unproven by the test — the unproven-claim problem persists in a new form. **mustFix.**
