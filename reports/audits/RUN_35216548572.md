## Summary

The candidate adds the V3-06 domain layer: `syncEngine` (cursor-based delta-only pull/push), `invitationService`, `unitChangeService`, `authorizationRules`, `costInstrumentation`, sync-state tables (`sync_cursors`, `sync_records`, `invitations`) in SQLite, repository sync methods, and a 731-line test suite. The domain services are well-structured and the delta-only cursor design is correct in principle.

However, the sync pipeline is **not functional end-to-end**:

- `applyDeltas` only writes pulled records into the `sync_records` buffer and never materializes them into business tables — remote changes never reach business data.
- `storeLocalRecords` has **zero callers** — local writes never populate the buffer, so `pushDeltas` always sends nothing.
- `resolveConflict`/`resolveConflicts` are dead code; `applyDeltas` performs blind last-write-wins by id.
- There is **no invitation UI** (no create/share/accept screen, no deep-link route) and **no group-options UI** (unit Minutes|Points and compensation toggle unreachable in-app, with a dangling "options du groupe" reference in `balances.tsx`).
- Authorization rules (tenant isolation, balance integrity) are only exercised in tests, not enforced in any data-access path.
- The V3-06 tests assert buffer/cursor mechanics only, never business-table materialization — which is why the non-functional pipeline passes the suite.

No V3-01..V3-05 regression, no chrono/premium/paywall, no domain Firebase coupling, no N+1 or massive listeners in the new code. Cost instrumentation with `COST_BUDGETS` is present and tested.
