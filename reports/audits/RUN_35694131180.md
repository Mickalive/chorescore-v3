## 2. The blocker and the repair rationale: SATISFIED

The trusted finalizer run 35692317866 failed at the Android API 35 install/launch/golden-path step. The exact step logs and the diagnostics artifact are not retrievable without admin rights (consistent with prior cycles). The candidate repairs the concrete E2E blocker with a timing analysis that is fully verifiable against the accepted baseline code and the previous audit's explicitly flagged weakness:

- `COLD_START_GRACE_MS = 450_000` (450s) — global cold-start grace from app launch.
- `STUCK_APP_THRESHOLD = 8` consecutive empty dumps before the stuck detector force-stops + relaunches.
- Each uiautomator dump takes **30-60s** on degraded API 35 x86_64 emulators (documented in the script).
- The stuck detector therefore fires at **450 + 8×30 = 690s** (best case) to **450 + 8×60 = 930s** (worst case).
- The previous Demarrer timeout was **1080s** (accepted in cycle 35686566515). Its recovery budget after stuck detection was **1080 − 930 − 17 = 133s** — below the documented **240s** first-cold-start worst case. Audit RUN_35686566515 flagged exactly this as non-mustFix finding #3: "Recovery budget after stuck detection is 133s (1080 − 930 − 17) for the relaunched app's cold start, below the documented 240s first-cold-start worst case."
- The finalizer run 35692317866 then failed — consistent with this failure mode: the stuck detector fired at ~930s, the force-stop + monkey relaunch took 17s, and the relaunched app needed up to 240s to cold-start plus up to 60s for a dump to detect the Demarrer button (total ~1247s), but the 1080s timeout expired first.
- The fix raises the timeout to **1260s**: worst case **930 + 17 + 240 + 60 = 1247s < 1260s**, leaving **73s headroom**, and fits within the GitHub Actions default step timeout (360 min).

Independent timing verification against the actual script constants confirms:

| Scenario | Outcome |
|---|---|
| Old timeout 1080s, worst-case stuck fire at 930s | **1247s needed > 1080s → TIMEOUT before recovery completes** (root cause) |
| New timeout 1260s, worst-case stuck fire at 930s | **1247s < 1260s → 73s headroom** |
| New timeout 1260s vs GitHub Actions step timeout | 21 min ≪ 360 min default |

After the force-stop + relaunch, the global grace (450s from relaunch, reset via `globalThis._appLaunchTime`) and `FORCE_STOP_RECOVERY_MS` (300s) protect the relaunched app from a second stuck-detector kill inside the window, so only one recovery cycle can occur within 1260s — exactly what the math covers.

The waitFor still requires the Demarrer button to actually appear — the timeout increase does not skip any assertion and does not mask a genuinely stuck app (the stuck detector still fires at 930s worst case and recovers).
