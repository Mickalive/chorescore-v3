## 3. Root cause and what the fix does

**Root cause (documented in the candidate):** after tapping "Demarrer", the app performs a demo sign-in that seeds data via SQLite. On slow API 35 x86_64 emulators this takes 1-3 min. The per-wait `graceMs` only protected the `waitFor('Demarrer')` call. The NEXT `waitFor` (e.g. `Appartement`) had no grace, so the stuck-app detector — 4 consecutive empty dumps at 30-60 s each = 2-4 min — fired during the sign-in phase, force-stopped a **healthy** app, and the relaunch + fresh 240 s cold start + sign-in cascade exhausted the step budget.

**The fix:**

| Mechanism | Before | After |
|---|---|---|
| Cold-start grace scope | Per-wait only (`graceMs` on Demarrer) | **Global**: `_appLaunchTime` set in `launch()`; ALL `waitFor` calls protected for `COLD_START_GRACE_MS` (450 s) since launch — covers cold start, demo sign-in and initial rendering |
| `STUCK_APP_THRESHOLD` | 4 (~2-4 min) | **8** (~4-8 min) before recovery after grace expiry |
| Grace reset on relaunch | — | `_appLaunchTime = Date.now()` on every force-stop/relaunch path (crash detector, pidof exit 1, APP STUCK) so a relaunched app gets a fresh window |

The per-wait `graceMs` remains as an additional overlay (`inPerWaitGrace || inGlobalGrace`). The `waitFor` timeouts remain the ultimate bound (900 s Demarrer, 300 s mid-path), so a genuinely stuck app still fails with diagnostics rather than hanging. The existing `FORCE_STOP_RECOVERY_MS` per-relaunch recovery is preserved unchanged.
