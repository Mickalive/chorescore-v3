## Findings

### Finding 1 — MUST-FIX: unified history pagination is incorrect (duplicates + unreachable older entries)
- **Path:** `app/(tabs)/add.tsx` (`loadHistory`, `activityEntries` merge)
- **Problem:** `loadHistory` fetches contributions and expenses with the same cursor, then advances the cursor to the **newer** of the two repo cursors. The stream with the older cursor re-fetches entries already shown on the previous page → duplicate rows in the merged history whenever both ledgers are active and both exceed PAGE_SIZE. Independently, the merged view is hard-capped at `PAGE_SIZE * 10 = 150` entries, so after loading more pages the view still shows only the 150 newest entries: older loaded history is unreachable while "Charger plus" keeps appearing.
- **Evidence:** Simulation of the exact `loadHistory` logic with 20 interleaved contributions + 20 expenses (PAGE_SIZE=15): page 2 re-fetches `c5` already shown in page 1 (merged count 41, unique 40, duplicate `c5`). Simulation of the merge cap: 600 loaded entries → view shows 150, oldest visible `c225`, `hasMore` still true. The new pagination tests cover single-repo pagination and the pure `paginateActivityLog` function only; the two-repo merged cursor path used by the screen is untested.
- **Required fix:** implement a single merged cursor-based pagination over the unified stream (one cursor over `occurredAt` across both repos, deterministic merge/dedupe), remove the hard 150-entry cap so every loaded page is visible, and add tests covering the two-repo merged pagination path (no duplicates, no gaps, older pages reachable).
- **Verification:** seed >PAGE_SIZE interleaved contributions and expenses, load 3+ pages through the screen's `loadHistory` logic, assert the merged list has no duplicate ids, no gaps, and the oldest loaded entry is visible; re-run `npm run check`.

### Finding 2 — MUST-FIX: contribution form does not conserve PersistentTask, date/heure, or share
- **Path:** `app/(tabs)/add.tsx` (contribution form + history actions)
- **Problem:** Constitution §5A requires conserving "PersistentTask / raccourcis de tâches", "date/heure" and "partage"; the V3-03 outcome repeats "Contribution conserve saisie libre, PersistentTask, Fait par/Fait pour, date, édition/suppression/partage sans chrono". The candidate's contribution form has none of the three: `persistentTaskId` is always null (no PersistentTask UI, although the demo fixture seeds a "Vaisselle" PersistentTask), `occurredAt` is always `todayLocal()` (no date picker), and history actions expose only Edit/Suppr (no share).
- **Evidence:** `add.tsx` — `cForm.persistentTaskId` initialized null and never set by any control; `occurredAt` initialized `todayLocal()` and never changed by any control; `historyActions` renders only "Edit" and "Suppr". `demoFixture.ts` seeds a PersistentTask "Vaisselle" that the Add screen never surfaces. `docs/NEXT_CYCLE.md` objective 1 lists "free label + PersistentTask + Fait par / Fait pour + date + edit/delete/share".
- **Required fix:** add PersistentTask shortcuts to the contribution form (prefill label/value/beneficiaries from the selected PersistentTask), a date/heure selector for `occurredAt`, and a share action for entries wired to the existing share port (honest adapter), keeping the form compact and chrono-free.
- **Verification:** reference-scenario check that a PersistentTask can be selected and prefills the form, that `occurredAt` can be changed and is persisted, and that a share action is present and wired to the share port; keep `npm run check` green.

### Finding 4 — Minor: redundant bounded fetches
- **Path:** `app/(tabs)/add.tsx` (effects + `loadHistory`)
- **Problem:** on mount and on every filter change, two effects both call `loadHistory` (4 paginated queries instead of 2), and `loadHistory` always fetches both streams regardless of the active filter. Bounded (2×15 per stream) but wasteful.
- **Required fix:** single effect keyed on `historyFilter`; skip the stream excluded by the filter.
- **Verification:** instrument repository call counts — opening the tab issues 2 paginated queries, a filter change issues 2, not 4.

### Finding 5 — Minor: custom split not pre-validated; edit/delete lack error handling
- **Path:** `app/(tabs)/add.tsx` (`submitExpense`, `submitEdit`, `handleDelete`)
- **Problem:** custom shares are not checked against the total in the UI (domain throws → generic Alert); `submitEdit`/`handleDelete` have no try/catch → unhandled promise rejection on failure.
- **Required fix:** inline validation of `sum(customShares) === amountMinor` before submit; wrap edit/delete in try/catch with a user-facing error.
- **Verification:** enter custom shares that do not sum to the amount → inline error, no write; simulate a failing delete → Alert, no unhandled rejection.
