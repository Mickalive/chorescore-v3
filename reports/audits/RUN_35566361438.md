## 3. What the fix does

The previous cycle (35559697736) added `COLD_START_GRACE_MS = 300s` to suppress the stuck-app detector during the **initial** cold start of the `Demarrer` wait. That grace period is tied to `waitStart`, so it covers only the first cold start. The gap: after a **force-stop + relaunch** mid-golden-path (crash detected by the pidof check, or the stuck detector firing on a cold start longer than the grace), the relaunched app needs a fresh cold-start window (documented worst case 240s), but the grace period has already elapsed — the stuck detector immediately counts empty dumps against the fresh cold start and force-stops again, resetting the cold start each cycle: an **infinite kill loop**.

The candidate closes exactly this gap:

1. `FORCE_STOP_RECOVERY_MS = 300_000` (5 min) — beyond the documented 240s cold-start worst case.
2. `globalThis._lastForceStopTime` — epoch timestamp of the most recent force-stop, shared across the whole golden path (initialized to 0 = "long ago" in epoch terms, so normal detection is unaffected until the first force-stop).
3. Every force-stop path records the timestamp:
   - `APP CRASHED` (pidof empty) → `globalThis._lastForceStopTime = Date.now()`;
   - `APP CRASHED` (pidof exit 1) → same;
   - `APP STUCK` → same.
4. Stuck detection increments `consecutiveEmptyMatchCount` **only** when `sinceLastForceStop >= FORCE_STOP_RECOVERY_MS`; within the recovery window it logs `FORCE-STOP RECOVERY: …s since relaunch` for diagnostics.
5. The pidof crash detector remains active during the recovery window — a genuinely dead app is still relaunched.

The new contract test verifies: the constant exists and is ≥ 240s; the tracking variable is used; all three force-stop paths record the timestamp; the recovery check guards the increment; the diagnostic logging exists.
