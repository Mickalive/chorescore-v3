## 3. The concrete emulator blocker: NOT repaired (must-fix remains)

### 3.1 Facts from the public API (run 35650859523)

- Step 5 "Trusted product, privacy and cost gates": success (70s).
- Step 6 "Build x86_64 release candidate for API 35": success (~10 min).

- Step 8+ skipped; diagnostics artifact `chorescore-v3-finalizer-diagnostics` (id 10663681034, 25.5MB) uploaded.
- `reopen-on-failure`: success.

### 3.2 No hard step timeout exists

- `chorescore-v3-finalize.yml` sets **no `timeout-minutes`** (job or step).
- `reactivecircus/android-emulator-runner@v2` `lib/main.js` runs the script via `exec.exec('sh', ['-c', script])` with **no timeout wrapper**; its only timeout is `emulator-boot-timeout` (default 600s) for the boot wait in `lib/emulator-manager.js` (`waitForDevice` polls `sys.boot_completed` every 2s before the script runs).

Therefore the step failed because the E2E script itself exited nonzero at 1259s — not because a step budget was exhausted.

### 3.3 Timing reconstruction pins the failure to the Demarrer waitFor

E2E script (`scripts/e2e-android.js`) fixed deadlines:

- `launch()` ≈ 120–150s (30s sleep + dumpsys polls + settle + pidof checks + uiautomator warm-up dump).
- `waitFor('Demarrer', 900000)` — **900s fixed window**.
- Later windows: `Appartement` 300s, `Ajouter` 300s, etc.

Wrapper overhead (pristine): boot check ~0–5s (action already waited) + settle 30s + health checks ~5–10s + APK install ~150–180s on a loaded API 35 emulator + post-install ~1s ≈ **210–235s**.

Sum: 210–235s (wrapper) + 120–150s (launch) + 900s (Demarrer timeout) ≈ **1230–1285s ≈ 1259s**. The step duration matches the **Demarrer waitFor timing out after 900s**: the app never showed the "Demarrer" sign-in button within 900s of launch.

Alternative scenario (Demarrer appeared, `Appartement` 300s timeout) would require wrapper ≈ 540s (boot ~100s + 3 full install attempts ~405s), which is possible but less consistent with the action's boot wait and the observed single-install behavior. Either way, the blocker is in the **app cold start / demo sign-in / initial render phase** (or dump fragility / System UI overlay), not in the wrapper.

### 3.4 Why the candidate's changes cannot fix it

The candidate's hypothesis is that wrapper overhead consumed the step budget. This is disproven:

- The step has **no hard timeout** (verified in the workflow and the action source).
- The E2E script's `waitFor` deadlines are **fixed** (900s Demarrer, 300s others) regardless of when the script starts.
- Reducing wrapper overhead by ~50–90s only shifts the failure earlier; the E2E still fails at the Demarrer timeout if the app does not render the button.

The candidate did not (and could not, from this environment) read the diagnostics: artifact download returns **HTTP 401** and step logs **HTTP 403** (admin rights) — both verified. The delta contains no logcat/dumpsys/result.json analysis and no change to the app cold-start/sign-in path or to the E2E script's mid-wait diagnostics.

- **Problem:** The candidate's wrapper-timing changes are safe improvements but do not address the actual failure: the E2E script's `waitFor('Demarrer', 900000)` timed out because the app never showed the "Demarrer" button within 900s of launch (cold start / demo sign-in / app crash / dump fragility / System UI overlay). - **Evidence:** Step 7 of run 35650859523 failed at 20m59s=1259s with all gates and the x86_64 build passing; timing reconstruction (wrapper ~210–235s + launch ~120–150s + Demarrer 900s ≈ 1259s) pins the failure to the Demarrer waitFor; no `timeout-minutes` in the workflow; action source shows no script timeout; artifact 401 / logs 403 verified.
- **Required fix:** Keep the pristine navigation and the safe wrapper improvements; repair the actual blocker — the app must reach the "Demarrer" screen within the E2E's fixed 900s window (investigate cold start / demo sign-in / SQLite seeding / splash / Hermes init) and/or add mid-wait diagnostics to `scripts/e2e-android.js` (periodic logcat/dumpsys during the Demarrer wait) so the next cycle can capture the exact failure point if it persists. Preserve V3-01..V3-07.
- **Verification:** The next trusted finalizer dispatch must pass the Android API 35 install/launch/golden-path step with `router.push('/add')` in place.
