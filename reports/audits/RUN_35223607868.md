## Must-fix findings

### 1. Sync pipeline not wired into the production SQLite path
- **Path**: `src/infrastructure/repositories/RepositoryFactory.ts` (`createSqliteRepositories`) + `src/infrastructure/repositories/SqliteRepositories.ts`
- **Problem**: On device, `createSqliteRepositories()` returns plain `SqliteSyncStateRepository` + plain Sqlite business repos: `applyDeltas` still only buffers pulled records into `sync_records` (cursor advances) and never materializes them into business tables; local business writes never call `storeLocalRecords`, so `pushDeltas` has no payloads. This is the previous audit's must-fix #1, still unfixed for the production path. Even in-memory, only contributions/expenses/todos/settlements are wrapped — writes to persistent_tasks, members, memberships and households never record dirty records.
- **Evidence**: `createSqliteRepositories()` constructs `syncState: new SqliteSyncStateRepository()` and plain Sqlite business repos with no `MaterializingSyncState` and no wrappers; `storeLocalRecords` callers exist only in `RepositoryFactory.ts` (in-memory) and the unused `SyncRecordingWrapper.ts`; `pullDeltas`/`pushDeltas`/`syncHousehold` have zero callers in `app/`/`src/features`; `LocalSyncAdapter` is an honest no-op (`isAvailable() === false`).
- **Required fix**: Wire materialization + dirty-record recording into the SQLite path for all 8 `SYNC_COLLECTIONS` (including persistent_tasks, members, memberships, households); add a contract test run against the SQLite implementation proving remote delta → business row readable and local write → `getDirtyRecords` payload.
- **Verification**: run the V3-06 e2e suites against the SQLite repository implementation, not only in-memory.

### 2. applyDeltas not transactional; cursor advances before materialization
- **Path**: `src/infrastructure/repositories/RepositoryFactory.ts` (`MaterializingSyncState.applyDeltas`)
- **Problem**: `inner.applyDeltas` (which advances the cursor) runs first, then `materializeDeltas` runs outside any transaction. A failure during materialization leaves the cursor advanced with records only in the buffer; the next pull will not re-fetch them — silent business-data loss. Violates "inside a transaction, then advance the cursor".
- **Evidence**: `const applied = await this.inner.applyDeltas(...); await materializeDeltas(repos, collection, records); return applied;` — no transaction wrapper; in-memory `withTransaction` snapshots only `todoRepo` and `contributionRepo`.
- **Required fix**: Materialize first, then advance the cursor, atomically (extend in-memory snapshot coverage; use `withTransactionAsync` on SQLite); roll back both on failure.
- **Verification**: failure-injection test asserting the cursor did not advance and business tables were not partially updated.

### 3. Tenant isolation and balance integrity not enforced in the data-access path
- **Path**: `src/domain/services/authorizationRules.ts` + `src/infrastructure/repositories/*`
- **Problem**: `requireHouseholdMembership`, `requireRole`, `assertLedgerWrite` have zero callers outside `authorizationRules.ts`; repositories accept any `householdId` without caller-membership context. Hostile tests exercise the pure functions, not the repository path. Previous audit's must-fix #4, still unfixed.
- **Evidence**: grep for the three functions outside `authorizationRules.ts` returns nothing; repository methods take no `userId`/membership parameter.
- **Required fix**: Enforce membership scoping in the data-access path (scoped repository facade or use-case checks) and route ledger mutations through append/revision/tombstone with `assertLedgerWrite`-style validation; hostile tests must go through the actual repository path.
- **Verification**: hostile tests calling the repository path with a non-member caller assert `AuthorizationError(CROSS_TENANT)` / `BALANCE_FALSIFICATION`.

### 4. Conflict resolution incomplete / still blind in places
- **Path**: `src/infrastructure/sync/SyncMaterializer.ts` + `src/infrastructure/repositories/SqliteRepositories.ts`
- **Problem**: (1) `case 'households'` does blind `repos.households.update(record.id, incoming)` with no `resolveConflict`; (2) local revision is fabricated as `0` in `resolveConflict` calls, so remote (revision ≥ 1) always wins and a local offline edit of the same id is silently discarded — de facto blind last-write-wins for accounting operations; (3) SQLite `applyDeltas` remains blind `INSERT OR REPLACE`.
- **Evidence**: `SyncMaterializer.ts` lines 134–203 pass `revision: 0` for the local side; households case has no `resolveConflict`; the e2e conflict test exercises the pure function, not the materializer.
- **Required fix**: Persist and pass the real local revision; apply `resolveConflict` to households (and members/memberships); make SQLite `applyDeltas` use the same deterministic resolution; add a materializer-level test where local revision > remote revision and assert the local version wins.
- **Verification**: materializer-level conflict test (local revision higher) + households delta test asserting deterministic resolution, not blind overwrite.

## Conclusion

The invitation flow, group-options screen, honest share adapter, deep-link route and meaningful e2e/hostile tests are delivered and green, and no previously accepted invariant regressed. However, the core V3-06 repair is incomplete: the sync pipeline is wired only into the in-memory test path, the production SQLite path still buffers without materializing and never records dirty records, `applyDeltas` is not transactional (cursor advances before materialization), tenant isolation is still unenforced in the data-access path, and conflict resolution remains blind for households and remote-biased everywhere else. Four must-fix findings remain → **repair**.
