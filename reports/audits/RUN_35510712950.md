## 4. Technical soundness of the repair

**Warm-up mechanism (sound):** `shell('uiautomator', 'dump', ..., { timeoutMs: 60_000, retries: 1 })` resolves to exactly 1 adb attempt with a 60s timeout (the `shell()` options-object handling pops the trailing options; `adb()` with `retries: 1` runs a single attempt and throws on failure). The `cat` is 1 attempt with a 30s timeout. The whole block is wrapped in try/catch with WARN-and-proceed, so a failed warm-up degrades to exactly the pre-repair behavior (first real dump is a cold start, handled by the existing dump-failure detection → `adbReconnect()` and app-alive check → relaunch). A successful warm-up forces the uiautomator server to initialize, so the first real `dumpUi()` in `waitFor('Demarrer', 600000)` succeeds quickly. The warm-up is positioned after the pidof check (~52s after monkey launch), when the app may still be on the splash screen — irrelevant for server warm-up, which is screen-independent.

**Cache interaction (minor defect, non-blocking):** `_dumpCache = { xml: warmupXml, nodes: [] }` — the nodes array is empty, so the first `findNodes('Demarrer')` cannot match from the cache; the loop spins on empty cache hits for up to the 30s TTL before a real dump. The comment's claim that the first `findNodes()` "reuses it instead of triggering another 30-60s dump" is inaccurate. Impact: up to 30s dead spin, absorbed by the 600s Demarrer window; the primary repair purpose (server warm-up) is achieved regardless. `tapNode()` invalidates the cache after the Demarrer tap, so post-transition dumps are fresh. Informational finding, not a mustFix.

**Test quality (effective):** The new test asserts the actual repair mechanism — `function launch()[\s\S]*Warming up uiautomator server`, try/catch wrapping, WARN handling, and the cache assignment. Reverting the warm-up block fails every assertion. Consistent with the file's established static-contract style (17 tests, all static). Not a weak test.

**Timing budget:** Worst case launch() grows from ~92s to ~183s; total worst case (boot 300s + settle 15s + health 10s + install 180s + launch 183s + golden path 1620s) ≈ 38.5 min, well within the 360-min job timeout and the failed run's 23m15s. Typical case ≈ 34 min.
