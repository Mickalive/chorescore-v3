## 4. Technical soundness of the repair

**Intent (sound):** The failure mode is real — on API 35 x86_64 the app process can stay alive while React Native is hung, and the pidof-based crash detector cannot distinguish that from a healthy app. A stuck detector with force-stop + relaunch recovery is the right direction, and the recovery sequence (invalidate cache, force-stop, monkey relaunch, 15 s settle, counter reset) mirrors the proven crash-recovery path.

**Implementation (broken):** The counter increment is not guarded on an actual dump having run. `findNodes(label)` → `dumpUi()` returns the cached result (30 s TTL) without touching `dumpFailures` on cache hits, so `dumpFailures <= previousDumpFailures` is true and the counter increments every 500 ms loop iteration. The threshold of 4 is therefore reached ~1.5–2 s after any single non-matching dump — not after 4 real dumps (2–4 min) as the comment claims. The detector cannot distinguish "app stuck" from "app still rendering / screen transition in progress", and force-stops a healthy app in exactly the slow-emulator scenarios the previous accepted repairs (warm-up cache with parsed nodes, 120 s/600 s waitFor windows) were designed to handle. The simulation demonstrates the consequence: 3 unnecessary force-stops during a normal 120 s cold start, each resetting the app's initialization.

**Test quality (insufficient):** The new test asserts only static strings (`APP STUCK`, `consecutiveEmptyMatchCount`, `STUCK_APP_THRESHOLD`, `force-stop`, `monkey`, counter resets). It passes with the buggy implementation and does not guard the actual logic — a contract test for this detector must assert that the counter only increments on a real dump (cache miss), e.g. via a `fromCache` flag from `dumpUi()` or a `_dumpCacheTime` comparison.

**package.json (hygiene, not blocking):** `react-native-view-shot` is unused in source and `react-native-worklets` remains installed transitively via `react-native-reanimated` 4.5.5, so the removal is functionally harmless and the Android build passed. However `package-lock.json` still lists both as root dependencies; `npm ci` tolerates the stale lock (verified empirically: exit 0, extra packages not installed), so the finalizer install step is not blocked. The change is unrelated to the stated objective and should either be accompanied by a regenerated lock or reverted.
