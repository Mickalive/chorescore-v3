## 2. The blocker and the repair rationale: SATISFIED

The trusted finalizer run 35670332996 failed to reach the 'Demarrer' screen within the E2E's 900s window on the API 35 emulator. The exact failure evidence is not locally retrievable (no `GH_TOKEN` in the Actions environment; no local logcat/artifacts), but the accepted previous cycle established the diagnostic branch and the ANR-overlay hypothesis: GitHub's API 35 emulators can surface a transient ANR dialog that completely covers the app, so `waitFor()` can never find the target label until the dialog is dismissed.

The candidate repairs the concrete blocker hypothesis:

- **SystemUI ANR** (`"System UI isn't responding"`) — emulator/system failure; tap `Wait` so the system recovers without killing it. This was the accepted baseline behavior and is preserved.
- **App-specific ANR** (`"ChoreScore isn't responding"`) — cold-start transient under React Native load (Hermes init / SQLite schema creation / demo fixture seeding). The app's main thread is likely blocked and will not recover within the 5-second Wait grace; without a force-stop the dialog reappears immediately, creating a Wait→ANR→Wait loop that burns the entire 900s timeout. The candidate taps `Wait` and then force-stops + relaunches, breaking the loop.

The rationale is sound: the previous SystemUI-only handler deliberately left app ANRs as real failures, which is exactly the failure mode that can burn the whole Demarrer window on a degraded emulator. The change is scoped to the E2E test script — no product code, no accounting, no sync, no analytics behavior is touched.

## 3. Kill-loop safety: VERIFIED

The app-ANR force-stop path cannot create an infinite kill loop:

- The path resets `globalThis._lastForceStopTime = Date.now()` and `globalThis._appLaunchTime = Date.now()`.
- The stuck detector only counts empty dumps toward `STUCK_APP_THRESHOLD` when `sinceLastForceStop >= FORCE_STOP_RECOVERY_MS` (300 000 ms) **and** the global cold-start grace has elapsed (`COLD_START_GRACE_MS` = 450 000 ms).
- After any force-stop, stuck detection is therefore suspended for at least 5 minutes, giving the relaunched app a fresh cold-start window — the same guard that already protects the existing stuck-app detector (lines 641–650).

## 7. Findings

### 7.1 Non-must-fix — ANR title detection is broader than the exact SystemUI string

- **Path:** `scripts/e2e-android.js` (`dismissAnrOverlay`, title detection)
- **Problem:** The detection now matches any `android:id/alertTitle` whose text includes `"isn't responding"` instead of the exact `"System UI isn't responding"`. This is broader, but scoped to the `alertTitle` resource-id, and the app-vs-SystemUI distinction is made by absence of `'System UI'` in the title. A false positive would require another system dialog whose title contains `"isn't responding"`; the action taken (tap Wait, retry) is benign and bounded.
- **Evidence:** `return resourceId === 'android:id/alertTitle' && text.includes("isn't responding");` then `const isAppAnr = !(anrTitle.text || '').includes('System UI');`
- **mustFix:** false
- **Required fix:** None for acceptance. Optional hardening: also require the `android:id/aerr_wait` button to be present before treating the dialog as an ANR.
- **Verification:** The Wait-button lookup already exists; the SystemUI path behavior is unchanged; trusted verification exit 0.

### 7.2 Non-must-fix — app-ANR force-stop is defensive robustness, not a proven reproduction

- **Path:** `scripts/e2e-android.js` (`dismissAnrOverlay`, app-ANR branch)
- **Problem:** The exact failure evidence from run 35670332996 is not locally retrievable (`GH_TOKEN` not set in the Actions environment; no local logcat/artifacts), so the app-ANR force-stop + relaunch is a defensive fix based on the documented ANR-overlay hypothesis rather than a proven reproduction. It is safe (kill-loop guards verified) and consistent with the existing stuck-detector recovery pattern, and it is backed by the trusted verification exit 0 and the contract test.
- **Evidence:** `if (isAppAnr) { globalThis._lastForceStopTime = Date.now(); globalThis._appLaunchTime = Date.now(); shell('am', 'force-stop', packageName); sleep(1000); shell('monkey', '-p', packageName, '-c', 'android.intent.category.LAUNCHER', '1'); sleep(15000); }` — guarded by `sinceLastForceStop >= FORCE_STOP_RECOVERY_MS` (line 642) and `globalGraceElapsed` (line 498).
- **mustFix:** false
- **Required fix:** None for acceptance. The next trusted finalizer dispatch will exercise the E2E with the new ANR handling; if the Demarrer blocker persists, the mid-wait diagnostics from the accepted previous cycle will pinpoint the exact failure point.
- **Verification:** Contract test asserts force-stop + monkey + `_appLaunchTime` reset for app ANRs and no force-stop for SystemUI; node --check OK; wrapper suite 24/24; trusted verification exit 0.
