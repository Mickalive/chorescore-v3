## 4. Technical soundness of each change

**adb restart removal (sound):** The pristine wrapper restarted the adb server process after boot and before the golden path. `kill-server` + `start-server` takes 6+s and the device-side uiautomator server must re-register with the new server; on degraded API 35 x86_64 emulators this stalls, so every `dumpUi()` returns empty XML and `waitFor('Demarrer', 600000)` burns out. The E2E script's `adb()` wrapper already retries with `adbReconnect()` on transport timeouts, and `launch()` explicitly avoids a reconnect before the Demarrer window. Removing the wrapper-level restart is consistent with the script's own resilience design. The replacement health loop is bounded (~12s max), `set -e`-safe (inside `if` conditions), and non-fatal.

**60s dump timeout (sound):** Each dump takes 30-60s on slow emulators; 45s killed dumps mid-transfer. 60s with 1 retry (≤120s per dumpUi cycle) still fits the 600s Demarrer window (~5 attempts worst case) and the 120s tab windows. The wrapper test extracts and asserts the numeric value (≥60s), which is a meaningful value assertion.

**Screenshot cache reuse (works):** `cacheFresh` mirrors `dumpUi()`'s own TTL logic, so the explicit check is redundant but harmless; the new `if (dump && dump.xml)` guard prevents writing empty XML files for failed dumps. Screenshots are diagnostic-only and never affect pass/fail.

**Crash-detection (BROKEN — mustFix):** `adb shell pidof <package>` exits 1 with empty stdout when the app process is dead. `execFileSync` throws on non-zero exit; the `adb()` wrapper retries 3× then rethrows; the `waitFor()` catch swallows it. The `if (!pid)` relaunch branch is therefore unreachable in the exact crash scenario the feature targets — the loop still burns the full timeout with empty dumps. The guarding test asserts only static substrings (`APP CRASHED`, `pidof`, `force-stop`, `monkey`) and passes regardless of behavior — a weak test per the audit criteria. The fix is trivial (check `err.status === 1` → treat as app-dead → relaunch; other errors → continue waiting) and the test should assert the error-status handling.
