## Must-fix findings

### 1. Expense modification detection ignores `currency` → currency-only edit corrupts the all-time money snapshot
`balances.tsx` lines 321-355 detect a modified expense only when `amountMinor`, `paidByMemberId`, `participantMemberIds`, `splitMode` or `customShares` differ. `currency` is not compared. The Add-tab edit form exposes an editable currency input (add.tsx lines 891-894) and persists it (line 532, `currency: eForm.currency.toUpperCase()`), so a user can change an expense from CHF to EUR without changing any detected field, then `emitDataChange('expense')` fires. The Balances handler classifies the entry as unmodified, keeps the old CHF effect and never applies the new EUR effect. The all-time `moneyByCurrency` snapshot then disagrees with `calculateFinancialBalancesByCurrency` full replay (and with the period views, which read the persisted entry), violating the release gate that materialized balances equal reconstructed balances.

**Evidence:** missing currency comparison at balances.tsx 326-331; editable currency at add.tsx 891-894; persisted currency at add.tsx 532; existing tests (lines 920-958) change amount only; `InMemoryExpenseEntryRepository.update` stores the new currency verbatim.

**Required repair:** include `currency` (and any other ledger-affecting field) in the modification condition; add a currency-only edit test asserting the old currency effect is removed and the new currency balance equals full replay, zero-sum per currency.

### 2. Required screen-level test still not delivered; header claim #8 unsubstantiated
The header now claims “**Screen-level**: delta handler re-reads only the changed collection, proving bounded repo calls (no full re-read on focus or signal)”. The tests do not import or render `app/(tabs)/balances.tsx` and do not touch `AppContext`: the “Balances screen subscribes…” test (lines 432-481) and “Balances subscribes… and unsubscribes cleanly” (lines 1071-1105) each build a local `Set` pub/sub stand-in, and the “screen-level delta refresh” section (lines 959-1070) exercises repository call counts against data-level handler logic. The tests would still pass if the screen reverted to a full re-read + full replay on focus or stopped subscribing, so they do not prove the claim they make.

A Jest probe confirmed the screen can be imported with `jest.mock('expo-router')`; a full render additionally requires provider/mock settling, so a genuine screen-level test is feasible but non-trivial.

**Required repair:** either (a) add a real screen-level/real-wiring test (mock `expo-router`, provide/mock `AppContext` with fake repos whose reads are counted, drive add/edit/delete through the signal, assert rendered delta + bounded reads), or (b) remove the word “Screen-level” and reword claim #8 to an explicitly data-level/handler claim that the tests actually prove. Do not leave a claim the tests do not exercise.

## Non-blocking observations

- **Settlement exactly-once test does not guard the fix.** The test at lines 557-620 claims to “simulate the exact handler wiring with React closure semantics” but applies the delta once directly and never simulates `emitDataChange('settlement')`/`handleDataChange`. It would pass against the pre-fix double-apply code. The code fix itself is independently verified, so this is not acceptance-blocking, but it should be strengthened in the same repair pass (spy on `emitDataChange` or assert idempotence of a second application).
- **Add-tab settlement branches are dead code.** `add.tsx` handles `cross-ledger-settlement` in `submitEdit`/`handleDelete` and emits `settlement`, but the Add-tab history is paginated with `paginateActivityLog(contributions, expenses, settlements=[], …)`, so settlements never appear there. Harmless, but the branch is unreachable.
- **Ref-comment wording.** The comment at balances.tsx 206-208 says refs are updated “synchronously while React closures still hold the previous” arrays; in practice refs are assigned during render. It does not change the verified behavior (the self-emit was removed), but the comment overstates the timing guarantee.
